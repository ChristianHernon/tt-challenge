# Frontend Engineering Challenge

## Scenario

In industrial IoT, digital twins represent complex hierarchies of physical hardware components (e.g., Factories → Production Lines → Heavy Machinery → Sub-components).

Because equipment lines are standardized, multiple distinct entities often share identical names across different zones (e.g., multiple production lines can contain an identical nested sub-component named `"Pump"` or `"Vibration Sensor"`). For operators on the plant floor, simple text search returns hundreds of duplicate names, creating massive confusion and errors.

Your goal is to build an elegant **Asset Search Component** in React that solves this disambiguation problem.

---

## Architecture Overview

The repository is split into two directories:

```
├── backend/            # Express API, SQLite database, and seed tooling
│   ├── seed.js             - Deterministic hierarchy generator (pet-food manufacturing vocabulary,
│   │                         ISA-95 tiers, ~2,000 assets).
│   ├── visualize.js        - CLI tree renderer with ASCII output, stats, duplicate report, and Mermaid export.
│   ├── database.js         - Database connection (node:sqlite DatabaseSync).
│   ├── server.js           - Express application.
│   ├── assets.db           - Generated SQLite database (created by `npm run seed`).
│   ├── tree.txt            - ASCII tree visualization output (generated by `npm run tree`).
│   └── package.json        - Backend dependencies and scripts.
└── frontend/           # Your React application (to be built)
```

---

## Objective

Build a React UI that allows users to search and confidently identify assets within a deeply nested equipment hierarchy.

The core challenge is **disambiguation**: assets frequently share identical names across different zones, so a result like `"Pump"` is meaningless without context. Your UI should make it immediately clear _where_ in the hierarchy each result lives — an operator should never have to guess which `"Pump"` they're looking at.

Search should support flexible matching:

- **Partial / substring / wildcard**: `"Motor"` finds all assets containing "Motor"; `"Motor*"` finds assets starting with "Motor"; `"*Motor"` finds assets ending with "Motor".
- **Exclusion**: Allow users to exclude terms from results (e.g., find "Pump" but not "Backup Pump").

Beyond that, this project is yours. The existing backend is a starting point, not a constraint — restructure it, extend it, swap Node for Go or Python, add endpoints, change the data model. Make the decisions you think are right and be prepared to talk through them.

## Getting Started

```bash
cd backend

npm install

# Generate the SQLite database (~2,000 assets, deterministic)
npm run seed

# Visualize the hierarchy (optional)
npm run tree

# Start the API server
npm start

curl -X POST http://localhost:5001/api/assets/search \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Deploying to Cloudflare Workers

The app deploys as one Cloudflare Worker with static assets. Vite's build output (`frontend/dist`) is served as static files; `/api/*` goes to `frontend/worker/index.ts`, which implements the two read endpoints the UI uses (`POST /api/assets/search`, `GET /api/assets/hierarchy`) over a JSON snapshot of the seeded database (`frontend/server/assets.json`). `node:sqlite` isn't available on Workers. The responses match the Express server's exactly. Config lives in `frontend/wrangler.jsonc`.

Workers Builds settings (Workers & Pages → Create → Import a repository):

| Setting | Value |
| --- | --- |
| Worker name | `tt-challenge` (must match `name` in `wrangler.jsonc`) |
| Root directory | `frontend` |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy` |

Node 26 (LTS) is pinned in `frontend/.node-version`.

Saving edits isn't implemented: the **Save** button shows the request payload instead of sending it.

```bash
# Local dev: Vite proxies /api to the Express server on :5001
cd backend && npm start
cd frontend && npm run dev

# Run the production build in the Workers runtime locally
cd frontend && npm run preview:cf

# Deploy from your machine instead of Workers Builds
cd frontend && npx wrangler login && npm run deploy

# After changing seed.js, regenerate the snapshot the Worker reads
cd backend && npm run seed && npm run export
```
